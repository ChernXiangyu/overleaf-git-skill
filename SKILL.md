# Overleaf through git

Overleaf projects can be cloned, pulled and pushed like a git repository. This is the only sane way to keep a
paper whose tables and figures are generated by code (Python, R, Stata) in sync with coauthors who write prose in
the Overleaf editor.

The thing to understand before anything else: **the git remote is a translation layer over Overleaf's own history
system, not a real git repository.** Overleaf docs are explicit about this. That single fact explains nearly every
limitation below — no branches, no tags, renames that lose comments, commits that appear out of nowhere.

Everything here is from Overleaf's documentation (sources at the bottom), except the final section, which is field
experience and is labeled as such.

## Setup

**Git integration is a premium feature on Overleaf Cloud.** The *project owner* needs a paid subscription (or beta
access). If clone fails with "Repository not found" and the URL is right, this is usually why.

**The URL.** A project at `https://www.overleaf.com/project/1234567` has git URL `https://git.overleaf.com/1234567`.
The authoritative URL is in the project itself: left sidebar → **Integrations** → **Git**. On Server Pro 4.0+ it is
`https://git@<your-server>/git/1234567` and an admin must have enabled the git-bridge.

**Authentication is a token, always.** Username/password auth no longer exists.

- Username: literally `git`
- Password: a git authentication token from [Account Settings](https://www.overleaf.com/user/settings)
- One token works for every project you can open, expires after **one year**, maximum **10 per account**
- A token is a credential. Never paste one into chat, a script, a commit, or a remote URL. If one leaks, delete it
  in Account Settings and generate a new one.

```bash
git clone https://git.overleaf.com/1234567 my-paper
cd my-paper
git config core.fileMode false          # Overleaf does not preserve the execute bit
```

Store the token in a credential helper so git stops asking. Overleaf's docs suggest `git config --global
credential.helper store`, which writes the token to `~/.git-credentials` **in plain text**. On macOS prefer the
keychain (this part is not from the docs, it is the platform-appropriate equivalent):

```bash
git config --global credential.helper osxkeychain     # macOS
# git config --global credential.helper libsecret     # Linux with libsecret
```

To let the user store the token without you ever seeing it, have *them* run the first `git clone` or `git pull` and
type the token at the prompt. The helper caches it and every later operation works unattended.

Migrating an old clone that still has a password-style remote:

```bash
git remote set-url origin https://git@git.overleaf.com/1234567
```

## The daily loop

```bash
git pull origin main        # get what coauthors wrote in the editor
# ... regenerate tables/figures, edit your own files ...
git add -A && git commit -m "update tables from the build"
git push origin main
```

**Commits are created just in time.** While people type in the Overleaf editor no git commits exist. One is
synthesized when you `pull` or `fetch`; your `push` creates one too. So a pull may produce a single large commit
covering hours of work by several people.

**Authorship is approximate.** If several people edited before a commit was generated, the commit is attributed to
whoever changed it last. To get a commit boundary at a meaningful point, label the version in Overleaf's History
(Overleaf → History → label). A labeled version gets its own commit hash, which is the docs' recommended way to
keep a legible history with coauthors.

**Never set up automatic polling.** Git clients that fetch on a timer hit the git-bridge rate limit. Pull when you
actually need to.

## Limitations that will bite you

| Limitation | What happens | What to do |
|---|---|---|
| **No branches** | Overleaf has one linear history, hard-coded to `main` (old clones: `master`) | Work on `main`. To use a local branch name, push with a refspec: `git push origin my-branch:main` |
| **File rename = delete + create** | Overleaf loses the file's **tracked changes and comments** | Never rename a file from git once collaborators comment. Rename in the Overleaf editor |
| **Folder rename** | Leaves an empty folder with the old name; renaming a folder and creating a file with that name in one commit is **rejected** | Split into two commits and delete the leftover folder |
| **Pushes can displace comments** | Docs: do not mix active git use with track changes/comments | See the decision rule below |
| **No symlinks** | A pushed symlink becomes a regular file and overwrites your local symlink on the next pull | Copy real files instead |
| **No tags, no Git LFS** | Silently unsupported | Use Overleaf labels instead of tags; keep binaries small |
| **Submodules** | A project can *be* a submodule, but cannot *contain* one | Use Overleaf's "add from another project" feature |
| **No execute bit** | Permissions are not preserved | `git config core.fileMode false` |

## The decision that matters: push, or edit in the editor?

Since a push can destroy comments and tracked changes on the files it touches, decide per file:

**Push from git** when the file is generated by your build (`tables/*.tex`, `figures/*.png`, a macros file) or when
you are the only person touching it. Nobody comments on a generated table, and regenerating it is the whole point.

**Edit in the Overleaf editor** when a coauthor writes or comments on that file. Use the editor's search and
replace (Cmd/Ctrl+F) for a surgical change; it touches only the matched text and survives concurrent typing,
because Overleaf merges edits character by character the way a real-time editor should.

This yields a one-way rule that works well for a paper backed by a code pipeline: **generated files flow
code → Overleaf and are never edited there; prose flows Overleaf → your backup copy and is never pushed.**
`scripts/sync_generated_files.sh` in this skill implements exactly that; read it before writing your own.

## Advanced operations

**Connect an existing local repository to a new Overleaf project.** Create a *Blank* project on Overleaf, delete
its `main.tex`, then:

```bash
cd my-paper
git remote add overleaf https://git.overleaf.com/1234567
git pull overleaf main --allow-unrelated-histories --rebase=false
git push overleaf main --set-upstream
```

Afterwards set the main document in Overleaf (Menu → Settings → Main document), since the blank project's was
deleted.

**Sync with GitHub/GitLab too.** Overleaf cannot talk to another host directly. Keep one local clone with two
remotes (`overleaf` and `origin`) and move changes through it. For GitHub specifically, Overleaf's own GitHub
Synchronization feature may be simpler.

## Several documents in one project

Overleaf compiles the project's **Main document** (Menu → Settings → Main document, or right-click a file → "Set as
main document"). That setting is project-wide: changing it changes what every collaborator sees.

You rarely need to change it, because **any file containing `\documentclass` compiles when it is the file open in
the editor and you click Recompile.** So a project holding both `paper.tex` and `memo.tex` works: leave the main
document on the one people open most, and open the other when you want to build it.

The main document should sit in the project root. In a folder, jump-to-location, word count and scripts like
`makeglossaries` break.

## Troubleshooting

| Symptom | Cause and fix |
|---|---|
| `Repository not found` | Wrong URL, or the owner has no premium subscription. Get the URL from Integrations → Git in the project |
| `Authentication failed` | Token expired (one year), deleted, or the username is not `git`. Generate a new token in Account Settings |
| Rate limit errors | A client is polling. Disable automatic fetch |
| `failed to push some refs` after a rejection notice | Someone is editing on Overleaf: `git pull --rebase origin main` then push again (see below) |
| `failed to push some refs`, no remote movement | Plan file-size/count limits, or an unsupported file (symlink, LFS). Check what the commit adds |
| Push hangs or times out | Large commit. Split it, and raise the buffer: `git config --global http.postBuffer 10485760` |

## From experience (not in the Overleaf docs)

- **A push is rejected whenever a collaborator is typing.** Overleaf commits the editor's state ahead of your push,
  so `push` fails with a non-fast-forward. If your commit touches only files that person is not editing, the fix is
  mechanical: `git pull --rebase` and push again, up to a handful of times. A sync script should do this itself
  rather than failing; a rebase of generated files onto their prose cannot conflict.
- **Keep the clone outside cloud-synced folders** (Dropbox, iCloud, OneDrive). A `.git` directory being rewritten
  by git while a sync daemon uploads it is a good way to corrupt the repository. Clone to `~/.cache/...` or
  `~/src/...` and copy files in from the synced folder.
- **Verifying "did my coauthor change anything?" via git is not conclusive.** Comments and tracked changes live in
  Overleaf's own data, not in the files, so `git pull` showing nothing does not prove the document is untouched.
  When it matters, look in the editor.
- **Announce renames.** Because a rename is delete + create, do them in the editor and tell the others, or the next
  person's pull will look like the file vanished.
- **A pushed figure that still looks old is usually Overleaf's image cache** (the compiler setting "Optimise images"
  reuses already-processed PNGs). Recompile; if it persists, use "Clear cached files" at the bottom of the logs panel.
- **When a number in the prose comes from your data**, consider writing it as a macro that the build regenerates
  (`\newcommand{\ztotal}{1,540}` in a generated `numbers.tex`) rather than typing it. Coauthors write
  `\ztotal{}` and the text cannot go stale when the data are revised.
